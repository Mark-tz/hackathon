# 参赛须知（通用规则）

> 适用于全部赛题 · 选手版草案 V0.1 · 文中数值为示例，以正式发布版为准
> 每队在报名截止前锁定**一个**赛题；各题独立排名，不跨题比较。

---

## 1. 你要交付什么

一个**离线运行的调度策略程序**。评测器在隐藏场景上逐事件推进仿真，在每个决策点把当前观测和**合法动作列表**发给你的程序，你返回一个 `action_id`。技术成绩 100% 由自动评测决定。

写出一个"能跑、比基线好一点"的策略很容易，参赛包里的基线改几行就能做到。拉开差距的是下面两点：

- 各赛题都有多个**场景族**，瓶颈和最优策略结构各不相同。正式评测**不告诉你实例属于哪个族**。
- 第 24 小时会发布一份**工程变更单（ECR）**，题目规格随之改变，你需要在 16 小时内重新适应。

---

## 2. 赛程（48 小时）

| 时间 | 事件 |
|---|---|
| 0h | 发布题面、参赛包 v1.0、开发集；现场讲解并演示基线 |
| 0–24h | **阶段 A**：开发；公开榜开放，每队每天 3 次 |
| 24h | 阶段 A 提交截止并封存；**同时发布 ECR**、参赛包 v1.1 和新开发集 |
| 24–40h | **阶段 B**：适应变更后的规格；公开榜重新开放 |
| 40h | 阶段 B 提交截止并封存 |
| 40–44h | 正式隐藏评测 |
| 44–48h | 技术复现展示，发布暂定榜，开启 24 小时申诉窗口 |

**正式总分 = 0.6 × 阶段 A 得分 + 0.4 × 阶段 B 得分**

- ECR 由独立评测管理员在赛前封存，开赛时公布其哈希。企业导师和现场技术支持都不知道 ECR 内容。
- 每个赛题文档都列出了该题 ECR 的**可能变更范围**和**不会变的部分**。
- 阶段 B 只有 16 小时。把开发、评测、分析流程做成**可复用的自动化流水线**，会直接决定你在阶段 B 的表现。

**阶段 C：自主进化分榜（如本届开放，另行通知）**
你提交的是开发流程（harness）本身，而不是策略。主办方用统一的模型网关、相同的 token 额度和算力，给它一个全新的题目变体，在无人干预的情况下运行 3 小时，再评测它产出的策略。阶段 C 单独排名、单独设奖，不计入正式总分。

## 3. 交互协议

- 每个实例启动一次策略进程，同一实例内进程保持运行（可以保留记忆），不同实例之间重启。
- 通过 stdin/stdout 交换 **JSON Lines**，每行一个对象。诊断信息写到 stderr，单个实例最多 1 MB。
- 消息流程：

```
评测器 → {"type":"init", ...静态信息, "seed":..., "limits":{...}}
策略   → {"type":"ready"}
评测器 → {"type":"decide","request_id":N, ...观测, "legal_actions":[...]}
策略   → {"request_id":N,"action_id":K}
   ……重复……
评测器 → {"type":"end","result":{...}}
```

- 各题的观测字段和动作类型见对应赛题文档。动作参数一律从 `legal_actions` 里取，不需要自己拼装。
- 出现以下任一情况，本局判为**无效**：`request_id` 不匹配、`action_id` 不在合法列表中、JSON 格式错误、超时、崩溃、内存超限。

## 4. 评分

### 4.1 单局得分：缺口闭合率

成本类题目（主指标越小越好）：

```
s = 100 × (C_base − C_team) / (C_base − C_ref)
```

产出类题目（主指标越大越好）：

```
s = 100 × (Q_team − Q_base) / (Q_ref − Q_base)
```

- `base`：参考基线策略的结果（源码在参赛包中），得 **0 分**。
- `ref`：主办方**全知离线参照解**，即事先知道全部未来事件后长时间求解得到的结果，得 **100 分**。在线策略一般无法超过它，但计分不设上限。
- 比基线差会得负分，下限 **−100**；**无效局记 −100**。
- 生成实例时保证基线与参照解之间的差距不小于基线值的 10%，避免分母过小。
- 开发集公开每个实例的 `base` 和 `ref` 值，方便你估算还有多少提升空间。

### 4.2 聚合

1. 每个实例用 3 个公开的策略种子各跑一次，取均值作为实例分。外生事件在 3 次之间保持一致。
2. 族得分 = 该族全部实例分的均值。
3. **阶段得分 = 0.7 × 全部族得分的均值 + 0.3 × 最差两个族得分的均值**
4. 正式总分按第 2 节的公式合成，保留 6 位小数。

最差族直接计入总分，所以只在部分场景族上调得很好的策略会被扣分。

### 4.3 示例（成本类，C_base = 1000，C_ref = 700）

| 你的结果 | 单局得分 |
|---|---|
| 1000（与基线相同） | 0 |
| 790 | 70.0 |
| 700（与参照解相同） | 100.0 |
| 1100 | −33.3 |
| 违规或超时 | −100 |

### 4.4 榜单与同分

- 榜单公布总分、各族得分、有效运行率、原始指标，以及 bootstrap 95% 置信区间。
- 同分时依次比较：有效运行次数、最差族得分。仍相同则并列。

## 5. 运行限额（正式评测）

| 项目 | 限额 |
|---|---|
| 资源 | 2 个专用逻辑 CPU、4 GB 内存，无 GPU，无网络 |
| 初始化 | 2 秒 CPU |
| 单次决策 | 1 秒 CPU |
| 单个实例累计 | 20 秒 CPU，40 秒墙钟 |
| 单个实例决策次数 | 20,000 次 |
| 镜像大小 | 不超过 2 GB；依赖在构建阶段装好，运行时不下载任何东西 |

单次决策上限是 1 秒，单个实例累计是 20 秒，所以你可以在策略内部做搜索或 rollout，但要自己分配预算。

## 6. 参赛包内容

| 组件 | 说明 |
|---|---|
| 仿真器源码 | 与正式评测器**等价**，提供两种接入方式：stdio 运行器（与正式协议一致）和 Python 进程内 SDK（速度快 1–2 个数量级，适合大批量试验） |
| 场景生成器源码 | 包含全部公开场景族的参数定义。正式集只对种子和隐藏族的参数组合保密 |
| 开发集 | 每个公开族 10 个实例，带族标签和 `base`、`ref` 值 |
| 信念仿真器 BeliefSim | 输入当前观测，按公开分布采样未来事件，可以在策略内部用来做 rollout |
| 基线策略源码 | 包括参考基线（决定 0 分）和若干简单规则 |
| 批量评测 CLI | `simkit eval --policy ./p --families all --n 200 --jobs 16`，输出每个族的得分、最差族、违规统计，以及与上一版本的差异 |
| 运行报告 `report.json` | 每局一份：资源利用率、等待时间按原因分解、违规码 |
| 回放器 | 甘特图、工件流转、状态时间线 |
| 其他 | 接口一致性测试、容器模板、FAQ |

## 7. 提交物

| 提交物 | 要求 | 用途 |
|---|---|---|
| 策略镜像 + 源码 | 阶段 A、B 各一份，截止时封存 | 正式评测；受控复核 |
| `evolution/` 进化日志 | 见下方格式 | 复核、"最佳自进化工程奖"评议 |
| `ANALYSIS.md` 问题分析报告 | 各场景族的瓶颈判断及证据；对隐藏集**各族得分的预测** | "自评校准奖"（预测误差最小者获奖） |
| `DEPLOY.md` 部署与试点说明 | 需要接入的设备信号、试点验证方法 | 产业合作评议 |

`evolution/lineage.jsonl` 每行记录一个候选版本：

```json
{"id":"g042-c3","parent":"g041-c1","time":"2026-12-05T14:20:00+08:00",
 "change":"瓶颈机床空闲时优先给它供料","eval":{"dev_mean":61.2,"worst2":38.5},
 "kept":true,"insight":"F6 族的损失主要来自缓冲阻塞，而不是机器人忙"}
```

"最佳自进化工程奖"和"自评校准奖"由评议产生，与技术排名分开，**不影响技术分**。

## 8. AI 使用与公平

- 开发阶段可以自由使用任何 AI 工具、agent 和自动化流程，评分不看是否使用了 AI。
- 主办方给每队发放**等额**的大模型 API 额度和一台 32 vCPU 云主机，供 48 小时使用。自带额外资源也允许，但需要在报名时申报。
- 正式运行时完全离线，禁止调用任何外部服务。可以在策略里嵌入本地模型，但它同样受第 5 节的限额约束。
- 禁止探测评测环境、读取隐藏数据或未来状态、利用未定义行为篡改环境。发现平台漏洞请通过统一渠道报告。
- 规则没有禁止、但出乎评委预期的合法策略，不会被追溯扣分。
