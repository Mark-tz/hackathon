# 备选题 A：存量设备按需运行与节能调度

> 选手版题面草案 V0.1 · 通用规则见 `00_参赛须知_通用规则.md` · 文中数值为示例

---

## 1. 背景

老旧产线不换设备，能不能省电？很多机床和辅机（冷却机、空压机、除尘）在没活干的时候仍然空转。但让它休眠也有代价：唤醒要耗电、要花时间，休眠越久，热机需要的时间越长，冷机加工还可能出废品。

你的任务是：**在保证所有任务按期完成的前提下，安排任务分配，以及设备的休眠和唤醒，使总用电量最小。**

---

## 2. 系统

| 要素 | 规格（公开范围） |
|---|---|
| 加工设备 | 3–5 台，部分设备之间可以互相替代，能效不同 |
| 共享辅机 | 1–2 台，例如冷却机。只要它服务的设备里有一台在加工或热机，它就必须处于运行状态 |
| 任务 | 每个实例 20–80 个，在线到达；每个任务有到达时刻、兼容设备集、名义加工时长、**交付期限** |
| 搬运 | 本题简化为：任务分配给某台设备后，由该设备的排队顺序处理，固定上下料时间计入加工 |

---

## 3. 设备状态与能耗

```
            ┌───────── assign / 队列非空 ─────────┐
            ▼                                     │
 [PROCESSING] ──完成──► [IDLE] ──sleep(L)──► [SLEEP_L] ──wake──► [WARMUP] ──► [IDLE]
                           └────sleep(D)───► [SLEEP_D] ──wake──► [WARMUP] ──► [IDLE]
```

| 状态 | 功率 | 说明 |
|---|---|---|
| PROCESSING | `P_proc`（与工件有关） | 加工中，**不可休眠** |
| IDLE | `P_idle` | 待机空转 |
| SLEEP_L 浅休眠 | `P_L`（较低） | 唤醒较快 |
| SLEEP_D 深休眠 | `P_D`（很低） | 唤醒慢 |
| WARMUP 热机 | `P_warm`（高） | 时长 = `f(休眠深度, 已休眠时长)`，**休眠越久，热机越长**（有上限），具体函数公开 |

**附加约束**

- 进入任一休眠状态后，至少停留 `min_dwell` 毫秒。
- 每台设备在每个实例里的启停次数不能超过 `max_cycles`。
- **冷机质量**：热机后的第一件工件，如果热机不充分（休眠超过 `T_cold` 但选择了"快速唤醒"），有 `p_scrap` 的概率报废，需要重做。报废时间和报废概率都公开。

**电量计算**：总电量 = 所有纳入的设备和辅机在每个状态下的功率 × 停留时长之和，从时刻 0 算到最后一个任务完成。单位为 Wh，转移瞬间不额外计能量。

---

## 4. 目标与约束

- **主指标**：总电量 E（Wh），越小越好。单局得分按成本类缺口闭合率计算。
- **硬约束**：所有任务都在各自交付期限前完成，满足驻留时间和启停次数限制。**任一任务超期，本局记为无效。**
- 只用于解释、不参与计分：峰值功率、各状态时间占比、辅机电量占比、报废次数。

## 5. 观测与动作（摘要）

```json
{"type":"decide","request_id":233,"t_ms":1260000,
 "devices":[{"id":"D1","state":"SLEEP_L","since_ms":1100000,"cycles_used":3,
             "queue":[],"warmup_if_wake_now_ms":42000}],
 "aux":[{"id":"CHILLER","state":"RUN","serves":["D1","D2"]}],
 "tasks_pending":[{"task":"T31","release_ms":1250000,"due_ms":1900000,
                   "compat":{"D1":180000,"D3":240000}}],
 "legal_actions":[
   {"action_id":0,"kind":"assign","task":"T31","device":"D1"},
   {"action_id":1,"kind":"wake","device":"D1","mode":"full"},
   {"action_id":2,"kind":"wake","device":"D1","mode":"fast"},
   {"action_id":3,"kind":"sleep","device":"D2","depth":"D"},
   {"action_id":4,"kind":"wait"},
   {"action_id":5,"kind":"wait_until","t_ms":1500000}]}
```

- `wait_until` 让你在没有新事件时也能在指定时刻醒来再做决策（例如定时唤醒），每个实例最多使用 500 次。
- 未来任务的到达时间不公开，只公布到达过程的类型和参数（如泊松过程、批次到达、班次模式）。

## 6. 场景族

| 族 | 公开特征 |
|---|---|
| E1 长间歇 | 订单稀疏、空闲时间长 |
| E2 短间歇 | 空闲时间短，休眠往往得不偿失 |
| E3 突发批量 | 订单成批到达，批次间隔有规律但有抖动 |
| E4 长热机 | 热机时间很长、功率高 |
| E5 紧交期 | 交付期限紧，休眠余地小 |
| E6 共享辅机 | 辅机功率大，**设备是否同时休眠**影响很大 |
| E7 冷机风险 | 快速唤醒的报废率高 |
| H1–H2 | 隐藏族，参数在公开范围内，机制组合是新的 |

规模：开发集每族 10 例；公开榜每族 2 例；正式集每族 5 例 × 3 种子。

---

## 7. 阶段 B ECR 范围预告

不超过下列 2 类：

- **目标函数**，例如改为分时电价下的电费，或者加入需量电费。
- **设备**，例如增加一台高效但只兼容部分任务的新设备。
- **约束**，例如设备之间有联动启停关系。
- **信息**，例如提前公布次日订单预报，但预报有误差。

协议框架、动作给出方式和计分公式的形式不变。

## 8. 参考基线

| 策略 | 说明 |
|---|---|
| `baseline_ref` | 任务分配给最早可用的兼容设备；空闲超过固定的 T 秒就进入浅休眠，有任务时完全唤醒。**定义 0 分** |
| `always_on` | 设备始终不休眠，只用于对照展示 |
| `ref` | 已知全部未来任务后离线求解的结果，**定义 100 分** |

成绩只能表述为"在给定仿真条件下的改善"，不能直接说成真实工厂的节电率。
